# TiledView Architecture

A deep dive into TiledView's virtual content space design for bidirectional infinite scrolling.

## Overview

TiledView is a UICollectionView-based component that enables bidirectional infinite scrolling.
Like chat UIs, it supports adding content both upward (older messages) and downward (newer messages).

## Core Concept: Virtual Content Space

### Basic Design

```
┌─────────────────────────────────────┐
│                                     │
│     Virtual Content Space           │
│     (100,000,000 points)            │
│                                     │
│  ┌─────────────────────────────┐    │
│  │                             │    │
│  │  Prepend Area               │    │
│  │  (items added to top)       │    │
│  │                             │    │
│  ├─────────────────────────────┤    │  ← anchorY (50,000,000)
│  │                             │    │
│  │  Initial Items              │    │
│  │                             │    │
│  ├─────────────────────────────┤    │
│  │                             │    │
│  │  Append Area                │    │
│  │  (items added to bottom)    │    │
│  │                             │    │
│  └─────────────────────────────┘    │
│                                     │
└─────────────────────────────────────┘
```

### Why This Design?

In a standard UICollectionView, adding items at the beginning causes the `contentOffset` to shift,
making the user's view position jump unexpectedly.

The traditional solution is to adjust `contentOffset` after prepending, but this has problems:

1. Visual jumps or flickering may occur
2. Difficult to adjust during animations
3. Race conditions may occur depending on timing

**Virtual Content Space design** does not compensate `contentOffset` for the height of newly prepended items.
It uses a large virtual space (100 million points) with an anchor point at the center (50 million points),
and places new items before the existing items' Y positions.
Explicit scroll requests, automatic scrolling to the bottom, and edge-content transitions can still change `contentOffset`.

### Prepend Behavior

```
Before:                          After:
┌──────────┐                     ┌──────────┐
│ Item 0   │ y=50000000          │ New Item │ y=49999900 (= 50000000 - 100)
├──────────┤                     ├──────────┤
│ Item 1   │ y=50000100          │ Item 0   │ y=50000000 (unchanged)
├──────────┤                     ├──────────┤
│ Item 2   │ y=50000200          │ Item 1   │ y=50000100 (unchanged)
└──────────┘                     ├──────────┤
                                 │ Item 2   │ y=50000200 (unchanged)
                                 └──────────┘

contentOffset: no correction for the inserted height
```

New items are placed **above** existing items, and the structural prepend preserves existing item Y positions.
This lets native scrolling continue without adding an offset correction for the inserted height.
Later self-sizing changes or viewport changes are separate layout operations and can change item positions.

### Append Behavior

```
Before:                          After:
┌──────────┐                     ┌──────────┐
│ Item 0   │ y=50000000          │ Item 0   │ y=50000000 (unchanged)
├──────────┤                     ├──────────┤
│ Item 1   │ y=50000100          │ Item 1   │ y=50000100 (unchanged)
├──────────┤                     ├──────────┤
│ Item 2   │ y=50000200          │ Item 2   │ y=50000200 (unchanged)
└──────────┘                     ├──────────┤
                                 │ New Item │ y=50000300 (= 50000200 + 100)
                                 └──────────┘
```

### Usage Example

```swift
struct ChatView: View {
  @State private var messages: [Message] = []
  @State private var scrollPosition = TiledScrollPosition()

  var body: some View {
    TiledView(
      items: messages,
      scrollPosition: $scrollPosition
    ) { message, state in
        MessageBubble(message: message)
    }
    .prependLoader(.loader(perform: {
      await loadOlderMessages()
    }) {
      ProgressView()
    })
    .task {
      messages = await fetchInitialMessages()
    }
  }

  func loadOlderMessages() async {
    let older = await fetchOlderMessages()
    messages.insert(contentsOf: older, at: 0)
  }
}
```

### Cell Size Measurement with IndexPath

To get accurate sizes before cells are displayed, TiledView uses an index-path-based size provider.

```swift
// Inside TiledView
tiledLayout.itemSizeProviderForIndexPath = { [weak self] indexPath, width in
  self?.measureSize(at: indexPath, width: width)
}

// Size measurement (reusing sizing cells)
private func measureSize(at indexPath: IndexPath, width: CGFloat) -> CGSize? {
  switch DisplaySection(rawValue: indexPath.section) {
  case .messages:
    guard indexPath.item < items.count else { return nil }
    return measureMessage(items[indexPath.item], width: width)

  case .prependLoader, .headerContent, .typingIndicator, .appendLoader:
    return measureAccessory(at: indexPath, width: width)

  case nil:
    return nil
  }
}
```

**Important**: The layout keeps item metrics by section, so accessory cells and message cells do not need a synthetic linear index.

### Serialized Display Updates

`TiledViewRepresentable` passes items, prepend and append loaders, the typing indicator,
and header content together to `TiledUIView.applySnapshot(...)`. A pending snapshot
retains those inputs without changing the data source used by an in-flight update.

`TiledUIView` owns one display update at a time. It first applies the snapshot's accessory
configuration, waiting for each structural accessory batch to complete, then diffs and
applies the message items. A full snapshot can require several UIKit batches; the queue
retains ownership until the complete sequence and its immediate completion effects finish.

Requested accessory configuration is separate from `DisplayedAccessoryState`, which
stores the typed SwiftUI content currently committed to each accessory section. Section
presence is derived from these optional content values, and both cell configuration and
size measurement read them. An insertion or removal changes committed content inside
its UIKit batch; reconfiguration refreshes it under the same display update owner. This
keeps a still-counted accessory row's content available until its removal is committed,
even when the requested loader or header configuration has already changed.

Delayed loader visibility changes and typing-indicator phase transitions enter the same
queue as accessory events. Their generation checks run when the event executes, so a
transition superseded by a newer state can be discarded. Consecutive waiting snapshots
are coalesced to the latest snapshot, but an accessory event between two snapshots keeps
its place in the queue. The active snapshot is allowed to finish.

For each structural batch, `performCollectionViewBatch`:

1. Retains the layout's pre-update metrics with `beginBatchUpdates()`.
2. Changes message items or committed accessory content inside `performBatchUpdates`'s
   updates closure, enqueues the matching layout mutation, and issues the insert/delete call.
3. Lets `prepare(forCollectionViewUpdates:)` apply the pending geometry mutation using
   the updated data source for measurement.
4. Releases the old metrics with `endBatchUpdates()` before advancing the display queue.

Content-only message updates change their payloads and call `reconfigureItems(at:)`
inside the updates closure, without retaining a structural metrics snapshot. Self-sizing
remains responsible for any resulting height changes. Replacement uses `reloadData()`
under the same queue ownership instead of an insert/delete batch.

The queue serializes data and accessory transitions. Native scrolling, explicit scroll
requests, and per-frame inset animation continue through their existing paths.

## Design Constraints

### Absolute Constraints

1. **Structural prepend does not compensate contentOffset**
   - The layout places inserted items above the existing message positions
   - This invariant concerns the insertion itself, not explicit scrolling or later size changes

2. **Layout must explicitly know prepend/append**
   - Y position calculation direction differs
   - Prepend: Place above existing items (Y position decreases)
   - Append: Place below existing items (Y position increases)

### Implementation Constraints

1. **Synchronization between item snapshots and section metrics**
   - One display update owns message and accessory mutations until its UIKit batches complete
   - Structural mutations change data source state and enqueue their matching layout update inside the same UIKit updates closure
   - The layout retains pre-update metrics while UIKit resolves the old and new collection-view states

2. **Size measurement timing**
   - `itemSizeProviderForIndexPath` is called after the data source state is updated
   - `measureSize` accesses the current section state, so order is important

## Why Declarative API is Challenging

### The Goal

```swift
// Ideal declarative API
struct ChatView: View {
  @State private var messages: [Message] = []

  var body: some View {
    TiledView(items: messages) { message in
      MessageBubble(message: message)
    }
  }

  func loadOlder() {
    messages.insert(contentsOf: olderMessages, at: 0)  // Just modify state
  }
}
```

### The Fundamental Problem

SwiftUI's declarative API only provides "current state".
However, TiledCollectionViewLayout needs to know "prepend vs append".

```
SwiftUI World:                    Layout World:
─────────────────                 ─────────────────
"Here are the items"              "Where did the new items go?"
[A, B, C, D, E]                   - Prepend? → Y positions shift up
                                  - Append? → Y positions extend down
                                  - Insert in middle? → ???
```

### Solution: Snapshot Diffing

TiledView solves this by comparing the currently displayed items with the latest
`[Item]` snapshot inside `TiledUIView`:

```swift
messages.insert(contentsOf: older, at: 0)
messages.append(newMessage)
messages = refreshedMessages
```
